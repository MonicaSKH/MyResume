屏東縣衛生所需求盤點 —— 導入前評估

CASE 01 · 現職 · 系統導入前的客戶端現況盤點

36 份問卷盤點 33 所衛生所現況,排出四階段上線優先序,成為客戶決策依據。

36份問卷 ~10所山地離島規則提早識別
情境 Situation

公司計畫把 xHIS 導入屏東縣多間衛生所,取代現行 PHIS、厚生等系統,但對 36 間衛生所的實際使用現況、系統痛點、地方特殊規則完全沒有第一手資料。

問題 Problem

若直接照理想規格開發,容易做出「沒人在用的功能」,也容易漏掉「山地離島等特殊身分別的部分負擔邏輯」這類邊界情境——等上線後才發現要重做,成本高很多。

行動 Action
  • 設計並發出 36 份問卷,逐一訪談收集回覆
  • 交叉比對重複填答,找出前後矛盾之處
  • 對第一批合作的 3 間衛生所(麟洛、萬丹、來義)另外做逐所深度訪談
  • 用「使用所數 × 法規強制性 × 缺了會不會停擺」三維度交叉分析,排出四階段上線優先序
  • 把山地離島衛生所的特殊部分負擔邏輯明確標注為「設計階段就要納入,不能後補」
  • 盤點五類遷移風險(操作習慣、資料轉換、山區部署、多廠商並存期、人員抗拒)並訂出對策
結果 Result

這份報告成為客戶端(衛生所)與內部團隊決定分階段導入順序與時程的依據。

36 份問卷 · 33 所衛生所回覆

~10 所山地離島特殊規則提早識別

VAC 疫苗管理系統 × NIIS 介接 —— 跨機關整合除錯

CASE 02 · 現職 · 跟政府系統對接的規格落差抓漏

逐頁比對 40+ 頁官方 API 規格書,在設計階段就抓出 3 項欄位缺漏,避免對接測試才被打回票。

40+頁規格書逐頁比對 3項欄位缺漏提早抓出
情境 Situation

公司要開發疫苗管理系統(VAC),需要跟疾管署的全國預防接種資訊系統(NIIS)做資料介接,但原始需求素材只有一份舊系統操作手冊跟一張流程圖,不是正式規格書。

問題 Problem

如果只憑內部 PRD/UI 草稿去對接,容易漏掉官方 API 規格書要求的欄位,等到跟 NIIS 實際串接測試時才被打回票,屆時修改成本高很多。

行動 Action
  • 用 python 工具(python-docx 讀操作手冊、pdfplumber 逐頁萃取官方 NIIS API 規格書)系統性整理素材
  • 依「誰做、什麼時候做、多頻繁做」拆解功能域,把初版模組收斂成界線清楚的 PRD
  • 逐條比對 PRD/UI 版本跟官方 API 規格書的每個欄位
  • 用 ui-preview 產生 3 種真實情境的互動 Demo(成人有健保卡、嬰幼兒無健保卡、學童接種 MMR)驗證流程涵蓋邊界情境
  • 過程中發現「兒童模式」原本用年齡自動判斷,但實際業務邏輯是「有沒有健保卡」才是判斷依據,及時修正,避免規格建立在錯誤假設上
結果 Result

這些落差在設計階段就修正,不是等到跟 NIIS 實際對接測試才手忙腳亂。

健保法規異動 —— 跨部門協調案例

CASE 03 · 和信治癌中心醫院 / 新光吳火獅紀念醫院 · 前後端連動修改的協調經驗

健保規則異動牽動前後端多系統,跨部門協調同步修改——這段經驗後來變成自動監控系統的起點。

質性案例 · 見完整故事
情境 Situation

在和信、新光任職期間主責門診/住院申報系統,健保局的申報規則不定期調整,是這份工作長期要面對的常態。

問題 Problem

新規則異動往往不是只有申報端要修改——連動的前端批價、掛號畫面如果沒有一起調整,會造成資料不一致,甚至被健保署整批退件。

行動 Action
  • 每次法規公告出來後,先分析異動實際影響到哪些子系統(不只申報端,還包括批價邏輯、掛號畫面顯示欄位)
  • 把異動範圍整理成清楚的規格,同步跟前端 RD、批價使用單位溝通,確保大家看到的是同一份影響分析
  • 協調各部門的修改時程與測試排程,確保上線前所有相關系統同步更新
  • 上線後追蹤申報結果,確認沒有因為規則沒改全而被退件
結果 Result

這段經驗也是後來在 AICS 開發「政府醫療法規每日監控系統」的起點——當年靠人工追法規異動、靠溝通協調各部門同步修改的痛點,後來被我做成自動分類、10 分鐘內自動建案的系統。

這個案例目前沒有精確的量化數字(例如年處理異動次數、退件率變化),如果你手上有實際數據,補給我後我會把 result-stats 換成真實數字。

全院 HIS 系統轉置上線 —— 多部門 Cutover 協調

CASE 04 · 新光吳火獅紀念醫院 · 跨廠商、跨部門的全院系統轉換執行

主導全院 HIS 系統轉置的跨部門 Cutover 協調,資料轉檔與教育訓練同步達標。

6h20m轉檔測試驗證 423人次受訓 174題反饋追蹤
情境 Situation

醫院要把整個 HIS 系統轉置到新平台,涉及多家廠商協作,橫跨醫事、保險、藥劑、放射、檢驗、護理、急診等全院近十個單位,是全院性的重大系統轉換,不是單一部門的專案。

問題 Problem

全院性 Cutover 只要有一個單位的停機配套措施沒談妥、資料轉檔任一環節出錯,就可能影響急診/住院醫囑、批價、藥局等關鍵流程,牽動病人安全;而且轉換窗口很短,沒演練過直接上線風險太高。

行動 Action
  • 擔任「上線轉換程序小組」院方負責窗口之一,主導與院內各單位溝通 Cutover Plan 並逐一取得共識
  • 定義資料轉換程序(舊系統日結/月結 → DB2 轉 Stage1 → Stage2 → 新 HIS,每一層都要驗證)
  • 定義新系統啟動順序、各系統人員編組分工、上線任務查核表
  • 規劃並執行多次上線轉換模擬演練,測試戰情室應變、關機轉檔、冒煙測試、資料比對全流程
  • 借用企業級 Cutover Plan 框架,在地化改寫成醫院場景的查核項目(例如把原本對外部客戶/供應商的通知,改成對消防局/衛生局/健保署/周邊醫院的通知)
結果 Result

資料轉檔流程分四道關卡逐層驗證,完成多次全流程模擬演練;同一時期的使用者教育訓練也同步達標。

CASE 05 · 新光吳火獅紀念醫院 · 非技術使用者的教育訓練與操作賦能

設計教育訓練教材與操作手冊,讓非技術使用者自己會用、敢用報表平台。

4份教材 3大操作面向
情境 Situation

指標/報表平台要正式交給醫品中心等非技術背景的醫院同仁自行操作,使用者原本習慣的是本機檔案、人工彙整,不熟悉 PowerBI 這類自助式報表工具。

問題 Problem

如果沒有教育訓練跟操作手冊就直接上線,使用者不會用、不敢用,上線後會湧入大量重複性操作疑問,拖慢正式導入的進度,也增加資訊部的救火成本。

行動 Action
  • 設計 PowerBI 教育訓練簡報,把資料分析流程講成使用者聽得懂的步驟(Excel/資料庫資料 → 資料整理 → 視覺化呈現)
  • 針對三種操作情境分別寫成圖文操作手冊:PowerBI 基本操作、報表(Reporting Services)設計操作、權限管理操作
  • 做一份範例報表(醫品中心指標範例)當成操作範本,讓使用者照著範例練習,而不是憑空想像
  • 把「使用者想分析什麼」到「資訊部產出圖表」的提需求流程畫成清楚的步驟圖,讓非技術同仁知道該怎麼跟 IT 溝通需求
  • 設計權限角色架構(依 folder / 角色 / 人員三層),讓後續管理者不用每次都靠個人記憶維護權限
結果 Result

產出一套完整的教育訓練教材與操作手冊,涵蓋資料存取、報表設計、權限管理三大操作面向,降低使用者上線後對 IT 的依賴,也讓「怎麼提需求」這件事有標準流程可循,不用每次都重新溝通一次。

  • Reference 轉換規則：FHIR 不用 ID 字串互相關聯,而是用 Reference 指向其他 Resource(例如 chartNo: "A123456" 要轉成 "subject": {"reference": "Patient/A123456"})。把這套轉換規則整理成對照表,病患、醫師、科別、就診四種識別都涵蓋。
  • 狀態值域不對等,需要合併對應：Fire 格式的掛號狀態有 8 種(Registered/Arrived/Consulting/UnderExam/Finished/Paid/Closed/Cancelled),但 FHIR Encounter 的 status 只有 7 個值,部分狀態(例如 Finished/Paid/Closed)需要合併對應到同一個 FHIR 值,並在文件裡明確記錄合併規則,避免日後對應邏輯各自為政。
  • 日期格式轉換：民國年格式(YYYMMDD)需要轉成西元格式(YYYY-MM-DD)才符合 FHIR 規範,整理成獨立的轉換模組需求,而不是每個 Resource 各自處理一次。
  • 缺漏欄位誠實列清單,不假裝規格完整：例如 FHIR Encounter 的 class(門診/急診/住院分類)是必填欄位,但 Fire 格式原本沒有對應欄位,明確記錄為「需在 Fire 格式加入 encounterClass 欄位」的待辦事項,而不是含糊帶過或自己亂填預設值。
  • 實作順序建議：依 Resource 之間的依賴關係排出實作順序——Patient 最先(其他 Resource 都會 Reference 到它),接著 Encounter,再來是對外交換用的 Claim 跟 Invoice,避免依賴關係顛倒導致重工。

PythonXML 驗證情境規則引擎

健保卡資料上傳的 XML 有嚴格的官方格式規範,而且規則會依「就醫情境」不同而不同 —— 同一個欄位在正常取卡時必填,換成預防保健或異常取卡情境,卻可能要求整個欄位都不能出現。 人工檢查很容易漏看這種依情境而變的規則,一旦送到健保署才被打回票,還得抓問題、修正、重傳,徒增等待時間。 這個工具在真正送出前先在本地掃一輪,把能抓到的錯誤都先抓出來。

讀取 XML(自動處理 Big5)→ 判斷就醫情境→ 套用對應規則逐欄檢核→ 交叉邏輯與格式檢核→ 產出驗證報告

三種就醫情境,規則各不相同

正常取卡一般門診就醫,多數欄位為必填
異常取卡讀卡失敗改手動輸入,部分欄位規則改變,序號格式也不同,且不可與慢連箋異動等特殊類別合用
預防保健健檢/篩檢類就醫,特定欄位(如給付類別)反而要求留空

  • CJK 友善的檢索邏輯：中文沒有天然分詞空格,自己寫了逐字切割加詞頻比對的檢索邏輯,不依賴額外的中文分詞套件;並設定「至少 40% 查詢關鍵字要出現在候選段落」的覆蓋率門檻,避免答非所問的段落被選中排序靠前。
  • 雙引擎備援：主力是 Gemini 2.5 Flash(免費方案,每天 1,500 次額度),中文理解與推理能力優異;Gemini 無法回應時自動切換 Groq(LLaMA 3.3 70B),速度快、品質也不錯,確保系統不會因為單一服務商斷線就整個查不到。
  • 只重建有變動的部分：用檔案雜湊值追蹤索引狀態,daily 排程只重新索引當天新增的公告,不用整個知識庫重建;新增 PDF 文件時只需手動跑一次更新指令,約 1-2 分鐘完成。
  • 簡單好用的 CLI 設計：qag 問題 直接問、qag 進入互動模式連續問答、qag update 增量更新、qag rebuild 完整重建(很少用到)。
  • 零額外訂閱成本：整套系統跑在本地端加上免費雲端 API 額度,不需要額外付費訂閱,所有答案都附原始文件來源供人工驗證,不是黑盒子。
