上線後的疊代:從「嚴重度」改成「行動」

三級分類上線一段時間後發現一個問題:RD 看到「Critical」只知道嚴重,還要自己對照異動類型才知道該做什麼。 於是重構成 4 個「行動分桶」,標籤直接告訴讀者要做什麼,不用自己再判斷一次:

[PR] 需改 codeCritical + LOGIC/CODE —— 程式邏輯異動,需要開 PR
[DB] 需調整設定Critical + PRICE —— 不改程式,但需更新資料節點 / 費率表
[xHIS] 相關公告Critical OPS + 所有 Important —— 系統相關,PM/維運知悉確認即可
[i] 無關公告與系統無關 —— 折疊顯示,不主動打擾

同時收斂 Jira 開票範圍:原本所有 LLM 解析成功的 Critical 項目都會開票,重構後只有真正「需要動作」 (需改 code / 需調設定)才開票,單純「知悉即可」的不再產生工單雜訊。

三管道同步通報：Critical 異動會同時發到 Jira 建票、Email 通知、並自動產生 Markdown PRD 推送到版本庫, 三個管道各司其職,不怕漏掉任何一邊。

健保卡上傳 XML 預檢工具

健康 / 資料驗證

上傳健保署前先在本地掃過一次 XML,依情境套用不同規則,連 ICD-10 格式、序號連續性、特殊識別碼都逐一比對。

PythonXML 驗證情境規則引擎

健保卡資料上傳的 XML 有嚴格的官方格式規範,而且規則會依「就醫情境」不同而不同 —— 同一個欄位在正常取卡時必填,換成預防保健或異常取卡情境,卻可能要求整個欄位都不能出現。 人工檢查很容易漏看這種依情境而變的規則,一旦送到健保署才被打回票,還得抓問題、修正、重傳,徒增等待時間。 這個工具在真正送出前先在本地掃一輪,把能抓到的錯誤都先抓出來。

讀取 XML(自動處理 Big5)→ 判斷就醫情境→ 套用對應規則逐欄檢核→ 交叉邏輯與格式檢核→ 產出驗證報告

三種就醫情境,規則各不相同

正常取卡一般門診就醫,多數欄位為必填
異常取卡讀卡失敗改手動輸入,部分欄位規則改變,序號格式也不同,且不可與慢連箋異動等特殊類別合用
預防保健健檢/篩檢類就醫,特定欄位(如給付類別)反而要求留空

檢查的七個層次

結構完整性確認 MSH 表頭段存在;若有醫令段(MB2)卻沒有健保資料段(MB1),直接判定整份退件
欄位存在性依情境判斷每個欄位是「必填」「選填」還是「不該出現」,三種情境各自對應不同規則表
值正確性固定值、就醫類別完整合法值白名單、異常/預防保健序號格式是否符合情境要求
交叉欄位邏輯調劑方式與醫令類別的合法組合、委託代檢是否有填機構代號、補卡/異常取卡相關欄位是否連動填寫
ICD-10 與手術代碼格式診斷碼與手術處置代碼不可含小數點(如 J06.9 需改 J069),且需符合「字母開頭 + 至少兩位數字」的格式
序號連續性醫令序號應從 001 起連續遞增,不連續就精確標出是第幾筆醫令、預期值是多少
長度與格式依官方公告的欄位長度上限逐一檢查,並抓出應該用全形卻誤用半形的特殊符號
真實案例挖出的規則：從某院所的實際錯誤報告裡發現,異常取卡(H01=B)一旦跟慢連箋異動(M07=AI)這類特殊類別合併使用, 22 筆記錄「全部」驗證失敗——後來把這個組合明確寫成規則,送出前直接攔下來,不用再等健保署那邊才發現整批出包。
連常見的手誤都抓得到：異常取卡時,系統要求特定欄位必須「剛好」填 MISS0000000000000000(20 碼); 最常見的手誤是少打一個 S 變成 17 碼的 MISS000000000000000,工具會直接標出實際碼數跟正確值的差異,一眼就看出問題在哪。
把退件風險留在本地：驗證報告會列出每筆記錄的錯誤與警告,精確標到欄位代碼、中文欄位名稱與記錄編號, 直接對應回原始資料就能修正,不用等健保署退件通知才知道哪裡錯。

技術細節
  • 處理健保署特有的編碼問題：官方 XML 常宣告 Big5 / CP950 編碼,但 Python 內建的 XML 解析器不支援,工具會先手動解碼再轉換,避免直接解析失敗。
  • 情境自動判斷：依「格式代碼」與「就醫類別」兩個欄位自動判斷屬於正常 / 異常 / 預防保健三種情境之一,不用人工分辨要套哪套規則。
  • 隱藏的交叉規則整理成表：官方公告裡「調劑方式」與「醫令類別」的合法組合是分散寫在文字說明裡的,這裡整理成明確的對照表,靠人工比對很容易看漏。
  • 兩種醫令包裝格式自動偵測：官方格式的醫令段有時是多個平行節點(每個各自包欄位),有時是單一節點底下包多筆子節點,工具會自動判斷是哪一種寫法再解析,不會因為系統產出格式不同就漏讀。
  • 精確比對特殊識別碼：某些情境要求欄位值必須「完全等於」特定的 20 碼字串,工具不是只檢查格式,而是逐字元比對,連少一個字元這種容易忽略的手誤都能抓到。
  • 結構化 Exit Code：0 表示全數通過、1 表示有記錄未通過、2 表示檔案本身有問題(解析失敗或找不到記錄),方便串進自動化流程當作卡關檢查點,而不只是給人看的報告。
  • 可批次處理：支援單一 XML 檔內含多筆就醫記錄,逐筆給出獨立的通過/失敗結果與問題清單。

從一份操作手冊、一張流程圖、一份政府 API 規格書,拆解出 5 份模組化 PRD,而不是把文件內容直接照搬。

功能域拆解python-docx / pdfplumberAPI 差異分析

有時候 PM 拿到的不是乾淨的需求文件,而是一堆原始素材 —— 舊系統操作手冊、手繪流程圖、政府 API 規格書。 規劃疫苗管理系統時,我先用程式把三份不同格式的文件內容萃取出來,再依「誰做、什麼時候做、多頻繁做」 三個維度把功能拆解、合併,最後產出 5 份界線清楚的 PRD 模組,而不是一份包山包海、誰都不想認領的巨型文件。

素材萃取→ 功能域拆解→ 初版 9 模組→ 合併收斂為 5 份 PRD→ 對照官方 API 差異迭代

拆解邏輯:三個維度定歸屬

VAC.Master管理員低頻設定 —— 疫苗代碼、批號、公費身份別條件維護
VAC.Administer護理師高頻日常作業 —— 施打當日資格核對與施打紀錄
VAC.Record行政查詢/補建 —— 事後管理、紀錄修正

從 9 份收斂到 5 份：初版依功能細節拆成 9 份模組,過於瑣碎;用「角色相同就合併」(批號維護跟疫苗代碼維護都是管理員做) 與「技術邊界獨立才分開」(NIIS 對接複雜度高,獨立成一份)兩個原則收斂,避免 RD 開發時模組邊界互相打架。
